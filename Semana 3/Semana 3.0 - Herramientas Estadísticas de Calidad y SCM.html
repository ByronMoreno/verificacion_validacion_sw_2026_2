Herramientas Estadísticas de Calidad y Gestión de Configuración (SCM)

En esta sesión dominaremos las 7 herramientas estadísticas clásicas de Kaoru Ishikawa adaptadas a la ingeniería de software moderna, profundizando en el Diagrama de Causa-Efecto (Espina de Pescado) y el Análisis de Pareto (80/20). Paralelamente, establecemos los cimientos de la Gestión de Configuración de Software (SCM): identificación de ítems de configuración (SCI), establecimiento de líneas base (baselines), ramificación profesional en Git y comités de control de cambios (CCB).

2 Las 7 Herramientas Básicas de Calidad en Software

Cómo el control estadístico de procesos resuelve el 95% de los problemas de calidad en equipos ágiles.

1. Diagrama Causa-Efecto

Identifica y clasifica de forma gráfica todas las posibles causas raíces que originan un defecto crítico de software.

2. Diagrama de Pareto

Principio del 80/20: el 80% de las fallas del sistema se concentran en el 20% de los módulos o causas identificadas.

3. Diagramas de Flujo

Modelan visualmente el proceso de desarrollo, revisión y despliegue (CI/CD) para detectar cuellos de botella y pasos sin valor.

4. Listas de Chequeo

Checklists sistemáticas para recopilar datos de inspección de artefactos o verificar criterios de aceptación (Definition of Done).

5. Histogramas

Visualizan la distribución de frecuencias de variables continuas: tiempo de resolución de bugs, cobertura de pruebas o tamaño de PRs.

6. Gráficos de Control (SPC)

Monitorean si el proceso es predecible en el tiempo calculando límites de control superior (UCL) e inferior (LCL) en métricas de sprints.

7. Diagramas de Dispersión

Miden la correlación matemática entre dos variables de software (ej. Complejidad Ciclomática vs Densidad de Defectos).

Categorías Adaptadas a Software
  • 🔹 Personas: Fatiga del equipo, falta de capacitación en el framework, rotación de desarrolladores, sesgos cognitivos.
  • 🔹 Procesos: Ausencia de code reviews obligatorios, criterios de aceptación mal definidos, despliegues manuales los viernes.
  • 🔹 Entorno y Herramientas: Dependencias desactualizadas, diferencias entre Docker local y Cloud, fallas de conectividad CI/CD.
  • 🔹 Requisitos: Historias de usuario ambiguas, cambios tardíos de alcance, criterios Gherkin ausentes.
  • 🔹 Código y Arquitectura: Alto acoplamiento, deuda técnica acumulada, falta de manejo defensivo de excepciones.
  • 🔹 Pruebas: Cobertura insuficiente en casos límite, datos de prueba obsoletos, ausencia de pruebas de integración.
Caso Real: Falla en Pasarela de Pagos

Durante un evento de Black Friday, el 40% de los pagos con tarjeta fueron rechazados erróneamente:

Causas identificadas con Ishikawa:
1. Código: Timeout estático configurado en 2 segundos (la API bancaria demoraba 3.5s por sobrecarga).
2. Pruebas: Solo se ejecutaron tests unitarios con mocks; nunca se probaron escenarios con latencia simulada.
3. Procesos: No se realizó un Load Test previo al evento.

5 Fundamentos de Gestión de Configuración de Software (SCM)

El arte y la ciencia de controlar la evolución de los artefactos de software.

¿Qué es SCM? (IEEE 828)

Disciplina que aplica dirección y vigilancia técnica y administrativa para: identificar y documentar las características funcionales y físicas de los ítems de configuración, controlar los cambios en ellos, registrar e informar el estado del cambio y verificar el cumplimiento de los requisitos.

Ítem de Configuración (SCI)

Cualquier artefacto de software creado o utilizado durante el ciclo de vida que se pone formalmente bajo control de configuración:
• Código fuente y scripts SQL
• Modelos y especificación de requisitos
• Casos de prueba y suites automatizadas
• Dockerfiles y pipelines YAML

Líneas Base (Baselines)

Una especificación o producto que ha sido formalmente revisado y acordado, que sirve de base para un desarrollo posterior y que solo puede cambiarse mediante procedimientos formales de control de cambios.

Jerarquía de Líneas Base en el Ciclo de Vida
Línea Base (Baseline) Momento del Ciclo de Vida Artefactos Aprobados y Congelados
Functional Baseline (Línea Base Funcional) Fin de la fase de Requisitos Documento de Requisitos de Software (SRS / User Stories aprobadas).
Design / Allocated Baseline Fin del Diseño Arquitectónico Diagramas C4, esquemas de bases de datos, contratos de API (OpenAPI/Swagger).
Development Baseline Durante la Construcción continua Versiones taggeadas de código y pruebas unitarias que pasan en CI.
Product / Release Baseline Entrega a Producción (Release) Binarios compilados, imágenes Docker selladas, informes finales de prueba y manuales.

6 Control de Versiones con Git y Gestión de Cambios (CCB)

Reglas de ramificación, branch protection y el Comité de Control de Cambios.

Estrategia de Ramificación y Branch Protection

En proyectos profesionales con V&V rigurosa, la rama main está protegida con las siguientes reglas inviolables:

Reglas Obligatorias en GitHub / GitLab
1. Bloqueo de Push directo a 'main'
2. Requerir Pull Request con al menos 1 Peer Review aprobado
3. Requerir que el pipeline de CI pase al 100% (Build + Tests)
4. Sin commits directos: Merge mediante 'Squash and Merge'
5. Versionamiento Semántico con Git Tags: v1.0.0, v1.1.0
El Comité de Control de Cambios (CCB)

Grupo formal de interesados (Project Manager, Líder Técnico, Líder de QA y Cliente) responsable de evaluar, aprobar o rechazar Solicitudes de Cambio (Change Requests - CR) sobre una línea base congelada.

Flujo del Cambio:
1. Solicitud formal de cambio con justificación.
2. Análisis de impacto (técnico, financiero y cronograma).
3. Decisión del CCB (Aprobado / Rechazado / Pospuesto).
4. Implementación en rama feature + Pruebas de Regresión.
5. Creación de una nueva Línea Base.
